# Objective

Prove the System Configuration and Change workflow by applying it to real reactive and proactive control-plane changes, without creating a second execution framework or swallowing #11 self-evolution governance.

# Evidence strategy

Do not launch one artificial mega-project for #15. Use representative real system changes as slices and accumulate evidence across them.

Suggested early fixtures:

- #14-driven reuse/replace decision for an external skill;
- a real configuration/instruction inconsistency;
- a bounded capability/configuration improvement from core execution.

# Execution phases per slice

1. Observe/request and orient to current canonical state.
2. Classify the problem before choosing the change surface.
3. Inspect built-in/local/external reuse options.
4. Propose the smallest change.
5. Create/attach a focused PLAN only if implementation complexity warrants it.
6. Implement/configure through normal bounded execution.
7. Validate deterministically; bounded repair on failure.
8. Review when consequence/uncertainty justifies it.
9. Reconcile CURRENT/DECISIONS only after acceptance.
10. Record repeated/material cross-project evidence as input to #11, not as automatic promotion.

# Validation

Across the evidence set, prove:

- at least one reactive and one proactive path;
- at least one reuse-before-creation decision;
- at least one evidence-backed choice of policy vs skill vs workflow vs script/tool vs no change;
- no silent durable mutation;
- accepted changes are traceable and reversible where practical.

# Stop conditions

Do not create extra workflow machinery solely to prove #15. If ordinary Issue/PLAN/PR mechanics already express the change lifecycle adequately, the correct result may be a semantic workflow with minimal new runtime packaging.

# Definition of done

The workflow is proven by real system-change evidence, with clear ownership distinct from #11 and no added bureaucracy beyond what improves change quality.
